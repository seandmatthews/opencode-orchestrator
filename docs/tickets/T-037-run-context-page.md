## What

Add one read-only dashboard route, **`GET /run/<id>/context`** (same surface and patterns as T-034/T-035: `src/dashboard.ts`, node:http, server-rendered HTML, zero client-side JS, GET-only under the existing `/run/` prefix parsing at `src/dashboard.ts:750-773` with `methodNotAllowed` 405 and `notFound` 404 faces), linked from the run page and from the job drill-downs' attempts section (plain `<a href>`). For one recorded run it renders:

1. **Store-backed face — direct read-only SELECTs, the only context data the store has.** The run's `attempts` rows: `job_id`, `attempt_number`, `state`, `started_at`, and `input_context_hash` (schema NOT NULL, `src/store/index.ts:181`; producer `src/runner.ts`), grouped per job, each job linked to its existing T-035 drill-down. These hashes are T-007 per-attempt input provenance and are **disjoint from packet fingerprints by design** (`src/rounds.ts` header: worker attempts never see a packet; the composed block feeds the round-2 planner prompt only, `src/runner.ts:234`). The page labels the two hash kinds differently and never conflates them.
2. **Report-backed face — honestly labeled as a report.json read via `runs.report_path`** (the pattern VERIFICATION.md:2785-2788 already anticipates; `report_path` is bound at ingest from the `reportPathOf` heuristic, `src/store/index.ts:1131`/`:1147`/`:1442-1449`). Renders the run report's `rounds` block (`src/types.ts:386-409` `RoundRecord`; producer `src/runner.ts:216-263`): per round — `round`, `executed`, `survivorIds`, and on a composed round `packetFingerprint` (rendered **verbatim, never recomputed**) and `renderedBlockPath` (a **verbatim pointer only** — never served, never linked to content; §26.5 stays carved). A visible label on this section: "report.json read via runs.report_path — not store rows".
3. **Producer-less §26.4 fields rendered as explicit no-producer markers.** Spec §26.4's fields (`docs/spec/inference-refinery-v2.md:1744-1764`) — token budget, mandatory/selected/distilled/excluded artifacts, source chain, and any plan/packet record — have **no producer anywhere**: the ingest upsert binds `jobs.context_plan_json` literal null among the ten nulls (`src/store/index.ts:1185-1210`, nulls at :1209; comment :1175-1176 "Every §6.4 policy column stays null — no producer"), no `context_plans`/`context_packets`/`artifact_lineage` table exists (schema is runs/candidates/gate_results/events/phases/jobs/job_dependencies/attempts/approval_gates/artifacts/probe_runs), the composer is pure/zero-I/O (`src/rounds.ts:1-9`), and `context inspect` (T-012) reads plan/packet files passed via `--plan`/`--packet`, never the store. The page says so per field instead of rendering fabricated structure (AGENTS.md #7).

A run whose report file is missing or unreadable still renders the store-backed face and says the report file is missing — 16 of 17 live runs are in this state today (see Why). Nothing is fabricated.

**Does NOT claim / carved off:** (a) **no ContextPlan/Packet persistence and no budget-ledger/claim/lineage rendering** beyond the markers — the producer (spec §27's `context_plans`/`context_packets` tables, the reserved `jobs.context_plan_json` column, or a rounds store table) is an engine/report-shape change owning its own Gate 2 run (trigger list VERIFICATION.md:2865); this ticket is the report-reading consumer slice, and the full §26.4 page remains that producer ticket's consumer successor (T-035:57-63, VERIFICATION.md:2775-2777). (b) No rendered-block or artifact **content** serving — pointers only (§26.5). (c) No candidate-lineage/generation rendering — no such records exist and decisions.md 2026-10-20 keeps `--rounds` at 1..2; T-014's context-claim lineage is not candidate lineage and is not rendered as such. (d) No fingerprint recomputation and no verdict surface — recorded hashes render verbatim; gates decide survival, models advise (decisions.md 2026-10-10). (e) Zero new npm dependencies, no client-side JS, no engine/store write (POST /approvals/decide stays the dashboard's only write).

## Why

The owner asked for the §26.4 context-inspector page as dashboard slice three. The premise is mostly false today, and this ticket is the honest shrink the evidence forces — every point below was verified by the repo scout this session (2026-10-21) against the code and the live store, and re-checked line-by-line while writing this ticket:

- Nothing persists ContextPlan/Packet rows: `jobs.context_plan_json` is bound literal null by the ingest upsert (`src/store/index.ts:1201-1210`); spec §27's `context_plans`/`context_packets`/`artifact_lineage` tables were carved with persistence itself (T-014:139-147, renewed T-030:88-90). A page SELECTing "the run's ContextPlan/Packet records" would SELECT nothing and dress it up.
- Budget accounting lives inside in-memory ContextPlans; the only ledger the CLI ever renders is over sandbox fixture files.
- Distilled-claim lineage rides inside packets real runs never produce; `context inspect`'s claim-chain output (`src/context-inspect.ts`) is file-driven, not store-driven.
- The only producer-backed per-run context data is (a) `attempts.input_context_hash` (store-backed, every dispatched attempt) and (b) the report.json `rounds` block (T-030) — `packetFingerprint` + `renderedBlockPath` ride the report only (`src/runner.ts:252-257`); the composer never touches disk (`src/rounds.ts:1-9`) and the runner writes only the rendered TEXT block (`round-2-context-block.txt`, `src/runner.ts:228-229`).
- Live reality, scout-queried this session against `C:\swarm\refinery.db`: 32 jobs rows, 0 with non-null `context_plan_json`; of 17 recorded runs, exactly 1 (20261021053700) carries a rounds block (fingerprint present, block file exists) and 16/17 report files are missing from disk — `report_path` is a heuristic reconstruction pointing into disposed verify sandboxes. Real content for 1 of 17 runs today; it grows with every `verify:full` run, which is a real 2-round run since T-030. Value is honestly marginal today (2/5).

This is exactly the shape VERIFICATION.md:2770-2794's carve note predicts: §26.4 is "BLOCKED ON A PRODUCER, not merely unpaged … the inspector page is that producer ticket's consumer successor", while VERIFICATION.md:2785-2788 sanctions rendering report-only data "honestly labeled as report.json reads via `runs.report_path`". Ticketing the honest slice now (a) gives operators the rounds/attempt-provenance view that actually exists, (b) puts no-producer markers where the operator questions §26.4:1758-1764 asks ("Why did this agent know this?") would otherwise find silence, and (c) names the producer ticket as the successor instead of letting the full §26.4 page get built on fabricated data.
